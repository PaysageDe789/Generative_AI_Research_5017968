## Classroom data notice

All examples are synthetic or placeholders, not actual participant data, collected evidence, or completed research findings. Confirm with the tutor that placeholders satisfy the exercise. Never upload identifiable responses, signed consent forms, or private media here.

## Folder structure and navigation

| Folder | Contents |
| --- | --- |
| `Literature_Review/` | Literature inventory, reference guidance, and reading-note template in `reviews/` |
| `Quantitative_Data/` | Survey-question template, fictional-data description, report outline, and example Python script in `Scripts/` |
| `Qualitative_Data/` | Interview guide, fictional transcript, unsigned consent outline, and thematic-analysis/visualisation plan |
| `Draft_Report/` | Proposal, conference-paper, and final-report outlines |
| `Additional_Materials/` | Participant-information outline and media inventory |

Start with the folder matching your material type and read its `readme` or `list`. Manage citations in Zotero; do not upload copyrighted papers without permission. Keep real raw and derived data separate in approved restricted storage, and never overwrite originals.

## File naming

Use `description_YYYY-MM-DD_vNN.ext`, for example `survey_questions_2026-09-14_v01.txt`. Use descriptive names, underscores, ISO dates, and explicit versions instead of ambiguous names such as `final_final`. Existing extensionless `readme` and `list` files are retained as folder guides; `reviews/date_keyword_etc.txt` is a reading-note template.

## Run the synthetic example

From the repository root, with Python 3 installed:

```sh
python3 Quantitative_Data/Scripts/synthetic_summary_2026-09-14_v01.py
```

The script prints the count and mean of three fictional embedded values. It does not read or write participant files.

## Collaboration guidelines

1. Fork the repository and clone your own fork with GitHub Desktop.
2. Fetch/pull before starting and create a clearly named branch.
3. Edit only agreed files or assigned logbook lines; inspect the diff.
4. Commit with a meaningful message and publish/push your branch.
5. Open a pull request targeting the reviewer's `main`, explaining your changes.
6. The reviewer checks and merges. Resolve conflicts by preserving intended contributions, removing markers, and checking for duplicates.
7. Fetch/pull again after merges to keep local work current.

## Access controls and backup

GitHub is for permitted non-sensitive files and version history. Store identifiable survey responses, real transcripts, signed consent forms, and private photos separately in institution-approved restricted storage such as UQ RDM, with controlled access and approved backups. A private GitHub repository alone does not replace institutional requirements.
